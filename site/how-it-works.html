How it works · drawn from the reference build at 0.1.1

One unit, end to end.

The never touches the code. It writes a contract, hands a session a worktree, reads the report the session wrote, re-runs the checks itself against the commit, and merges or routes. Everything on this page is what packages/regulator/src/controller.ts and the Pi host's session extensions actually do, and none of it is aspirational.

This page runs deeper than the others on purpose. Where the product and course pages summarize, this one shows the actual sequence diagram, two state diagrams (one for a single unit's own lifecycle, one for how a whole software change moves through six different unit types), the real contract and report JSON, a table of every extension hook a session fires, and the exact files an instance writes to disk. If you came here to see the mechanism itself, this is the page.

Vocabulary — for this page specifically Full glossary ↗
unit
The smallest piece of dispatched work — one contract, one session, one verdict.
worktree
A git checkout on its own branch, dedicated to exactly one unit, so units never collide.
work contract
What the unit is authorized to decide: fixed, delegated, or left explicitly unresolved.
lease
A time-limited claim on that worktree — it expires if whoever holds it goes quiet.
closeout gate
The check that re-runs the unit's tests itself before trusting its report.
obligation
A signal — often "a person needs to answer this" — that stays open until resolved.
attempt
One immutable, claimed run of a unit against a specific revision. It doesn't finish or cancel the work by itself — routing decides what happens next.
workload
A declared set of unit types for one kind of job — six of them, below, for software.
capability profile
A bounded grant of tools and writable paths a unit runs under — a positive list, not a persona.
evidence
A check result tied to the exact commit it ran against — never just "the tests passed," always "the tests passed, at this revision."
technical verdict
Pass, fail, or inconclusive — decided mechanically from evidence, never from what the unit says about its own work.
reintegration
Bringing an isolated unit's work back into the main line — the moment two units' assumptions about the same file can collide.
The loop

Orchestrator, session, worktree, stores

Five participants. The orchestrator is the S3 loop in the base checkout. The session is Pi with the host's extensions loaded, running in a git worktree that belongs to exactly one unit. The domain, which is the repository, sits on the far right and is only ever read as a domain, never as state.

  1. ContractThe orchestrator checks the contract (shape, consistency, a unit type the workload declares) and records the unit under it. The contract file is immutable; a new version is a replan, not a retry.
  2. DispatchA lease and a worktree are taken for the unit (a branch unit/u1 checked out under .regulator/worktrees/u1), and a Pi session starts there with the definition's checkpoints loaded and nothing the project supplies.
  3. SessionThe gates find the unit the way S3 recorded it: the lease whose resource is this worktree, then the contract from the store. The contract becomes a system-prompt section (advice) and a typed session entry (state).
  4. SessionThe model works inside the gates. Writes need the 's grant and a live lease, and must not touch identity or protected paths. The budget meter counts every turn, tool errors become observations, and run_tests results are stamped with the revision they ran at.
  5. SessionIt commits and calls report_result, the only way a unit ends well. The report is refused unless it honours the contract and cites runs that happened here, on the committed tree, and passed.
  6. VerifyThe orchestrator reads the report, never the diff, and re-runs the workload's checks itself against the commit. and the go to the audit log; a claim in the report that the host contradicts is named.
  7. CloseOn pass, the branch is merged into the base, the worktree removed, the lease released. On anything else the is recorded as it ended and the unit is blocked.
  8. RouteA blocked unit is routed under the versioned recovery policy: the cause is classified from the orchestrator's records first, then S2's signals (an , say), then the session's observations. The Nth occurrence takes the Nth action, and retry and repair spend attempts until they become escalate at the ceiling.

The unit's own states

The same journey, drawn as a state machine

The sequence diagram above shows who calls whom, in what order. This is the complementary view: what the unit itself can be, at any moment, and exactly what moves it from one thing to the next. There are only six values a 's status field can ever hold: contracted, dispatched, reported, closed, blocked, aborted. They are defined once in packages/protocol/src/execution.ts and enforced everywhere that reads or writes a unit record. Any other value in that field is a bug.

Reported is not "the model finished"By the time a unit's status becomes reported, the host has already re-run every check itself and they already passed, because closeVerifiedUnit only sets this status right before attempting the merge. A unit whose checks fail never becomes reported at all; it goes straight from dispatched to blocked.
Waiting isn't a sixth statusIt's blocked plus an open that vetoes the next dispatch. The schema stays at six values; the veto lives in the obligation ledger, checked fresh on every dispatch attempt.
Paused is a special case of blockedWhen a unit asks a person a blocking question and nobody answers before the session ends, the attempt's outcome is recorded as paused and the unit's status is blocked, with the reason spelled out in plain language. regulator answer turns the obligation from open to resolved and lets the next dispatch through.
The full decision logic is nextThis diagram shows where a blocked unit can go. The recovery section below shows how the choice between retry, repair, remediate, replan, clarify, pause, escalate and abort actually gets made.

A work contract

What a unit is authorized to decide

This is the real first contract from the lab, packages/regulator/contracts/fix-known-issue.json, unchanged. A contract is not a task description: it allocates decisions. Some are fixed before the unit runs, some are delegated within bounds, and some are explicitly nobody's yet, and the report is refused if it settles one of those.

{
  "kind": "task",
  "id": "tc-fix-known-issue",
  "version": 1,
  "unitId": "u1",
  "unitType": "implement",
  "workload": { "name": "software-development", "version": 1 },
  "objective": "Fix the known issue described in the README so that
                the project's own test suite passes.",
  "contribution": "First contracted unit against the fixture: proves
                   the loop before the loop is trusted with anything larger.",
  "constraintRefs": ["reg.authority.vendor-write-gate.v1"],
  "fixed": [
    { "id": "f-signature", "subject": "public signature of slugify",
      "decision": "slugify remains a single-argument function returning
                   a string; no options object, no second parameter.",
      "authorityRef": "S3 planning decision P1 (lesson 06)" },
    { "id": "f-vendor", "subject": "vendored helper",
      "decision": "vendor/left-pad.js is not modified, wrapped, or replaced.",
      "authorityRef": "reg.authority.vendor-write-gate.v1" }
  ],
  "delegated": [
    { "id": "d-helpers", "subject": "private helper decomposition",
      "bounds": "Private helpers inside src/slugify.js only;
                 no new modules, no new dependencies." },
    { "id": "d-tests", "subject": "additional test cases",
      "bounds": "May add cases to the existing test files under test/;
                 may not delete or weaken an existing assertion." }
  ],
  "unresolved": [
    { "id": "u-unicode", "subject": "non-ASCII input",
      "reason": "Nobody has decided whether accented characters are
                 transliterated, stripped, or preserved.",
      "handling": "defer" }
  ],
  "expectedEvidence": [
    { "id": "e-tests",  "description": "run_tests reports every test passing",
      "class": "test",    "required": true },
    { "id": "e-checks", "description": "run_checks reports every check passing",
      "class": "command", "required": true }
  ],
  "provenance": { "createdBy": "S3", "createdAt": "2026-09-22T00:00:00.000Z" }
}
version · unitTypeThe store keeps contract.v1.json immutably. The unit type selects the the session runs under and the checks the orchestrator re-runs at closeout, both from the workload definition; the contract itself names neither a model nor a tool.
fixedDecisions already made, with the authority that made them. The report may not silently deviate: a deviation from a fixed decision must be declared and becomes a blocking signal for S3. f-vendor is also a gate; the contract restates it so the unit knows why the gate refuses.
delegatedDecisions the unit makes, within bounds. The report must say what it chose for each one; a missing choice is refused at the tool and again at close.
unresolvedDecisions nobody has made. The unit may preserve them (leave the behaviour untouched) or surface them (report what it found); there is no settled. A report that omits u-unicode is refused: "settled silently or forgotten".
expectedEvidenceThe criteria the binds host-run evidence to, by class. The unit's own run_tests call satisfies the report's shape; only the orchestrator's re-run at the committed revision satisfies the criterion.

The result report

What the unit says back, and who checks which field

The report is the only thing the orchestrator reads about the work. It is written by a typed tool the session calls once, checked against the exact contract version at the tool and again at close, and then contradicted or not by evidence the orchestrator produced itself.

{
  "contractId": "tc-fix-known-issue", "contractVersion": 1,
  "unitId": "u1", "attempt": 1, "reportedAt": "…",
  "summary": "Collapsed repeated separators and trimmed dashes; all tests pass.",
  "evidence": [
    { "class": "test",    "ref": "run_tests",  "observation": "4 passed, 0 failed" },
    { "class": "command", "ref": "run_checks", "observation": "2 ok" }
  ],
  "delegatedResults": [
    { "decisionId": "d-helpers", "choice": "one private collapse() helper" },
    { "decisionId": "d-tests",   "choice": "added two edge cases" }
  ],
  "unresolvedOutcomes": [
    { "decisionId": "u-unicode", "outcome": "preserved",
      "note": "accented input still passes through untouched" }
  ],
  "emergentDecisions": [
    { "subject": "trailing whitespace", "choiceOrQuestion": "trimmed it",
      "consequenceIfWrong": "low" }
  ],
  "deviations": [],
  "residualUncertainty": []
}
attemptOne report per contract version and attempt: a repair attempt writes its own, and none is revised.
evidenceChecked for shape at the tool (every required class present) and for provenance before the tool runs (the run happened in this session, at HEAD, on a clean tree, and passed). Then the closeout gate re-runs the checks and, if they fail, lists this claim as contradicted.
delegatedResults · unresolvedOutcomesChecked at the tool and at close: every delegated decision has a choice; every unresolved decision has an outcome of preserved or surfaced.
emergentDecisions · deviationsThese are not gated, only recorded: a high-consequence emergent decision and every deviation become typed signals for S3 at close.

Three stores

Nothing reads its own progress off the domain

INV-005. Execution state, regulatory state and the domain are three different things with three different owners, and no arrow below is inferred from another. The orchestrator knows what it dispatched because it wrote it down, not because it looked at the diff. The direction matters too: the definition is the product (the registry, profiles, policies, workloads and the identity seed, shipped as a package); an instance is one repository that regulator init installed it into, and nothing flows back from an instance into the definition except by a person's decision, made with regulator identity promote under S5 authority.

Typed channels

A signal is not an audit; a proposal does not mutate policy

Everything the functions say to each other is a typed message, and the type carries the control semantics: who may send it, what it means, and who it is routed to. The routing policy then declares, per kind, the severity at which a message stops being trace and opens an obligation for someone, with floors that raise anything naming a protected invariant to blocking, whatever the sender said.

KindFromMeansEmitted byRouted to
operational-signalS1something about the work: a blocker, a deviationthe loop, from a report's emergent decisions and deviations; a session whose rendered identity was truncatedS3
uncertainty-signalS1residual uncertainty with a reported impact; the policy maps the claim to a severitythe loop, from a report's residualUncertaintyS3
coordination-signalS2a lease expired, a conflict, oscillationthe thrash detector in the session; reintegration on a conflict, textual or found by the pre-merge trialS3
audit-findingS3*evidence contradicts a claim or an invariantthe bash watch on a restored protected path; the closeoutS3
intelligence-signalS4the environment changed, or willreport_intelligence in a research unitS3
policy-proposalanya request to change identity or policy; never a mutationpropose_policy_changeS5

constraintS5, S3a boundary a unit runs under, stated ahead of the workdeclared, not yet emitted: a unit's constraints reach it as the contract's references and the rendered identitythe unit
One severity line for every kindinfo, advisory, blocking, critical. The protocol, not the sender, fixes what each one means: an advisory is noted as trace with the reason. A blocking message opens an obligation that holds the unit it names until someone dispositions it, and a blocking finding with no unit holds every dispatch.

Recovery

What happens on attempt two, and on attempt six

A blocked unit is not retried; it is routed. The cause is a closed set, classified in a fixed order. The action comes from a versioned policy, by occurrence, and the attempt ceiling is the floor under the lattice.

The algedonic path

When a unit needs a person

A person's attention is the scarcest thing the system spends, so the way to it is narrow. A unit asks through one typed tool, under a contract that says what happens next; the loop reaches a person only when recovery has nothing left to try. Either way what is owed is an obligation, and silence is never an answer.

Inside a session

Where the gates sit in a session

A unit's session is plain Pi with eleven extensions loaded in order (tools, profiles, coordination, contract, budget, recovery, evidence, authority, intelligence, identity, algedonic), each hooking a handful of lifecycle events. Hover or tap a point on the line for what runs there. A solid red marker can refuse a tool call or halt the session; a hollow marker only records what happened.

On disk

An instance, after one routed unit

Everything the orchestrator and the regulators know lives under .regulator/ in the base checkout, ignored by git. The repository itself is the domain. This is what a fixture looks like after a unit was blocked at verification, repaired, and closed.

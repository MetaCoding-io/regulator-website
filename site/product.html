Architecture

regulator

An agent harness built on Pi, with a typed VSM control plane layered on top of it — designed against one recurring failure mode of autonomous agents: architectural drift that outruns anyone's ability to review it.

What VSM is, and why it matters here

Stafford Beer's Viable System Model comes out of management cybernetics, not software: it asks what any system — an organism, a company, an autonomous agent — needs structurally to keep operating as its environment keeps generating more variety than it can be made to predict. Beer's answer is five functions plus an independent audit: operations that touch the world (S1), coordination that keeps them from colliding (S2), control that decides what happens next (S3), intelligence that watches the environment and the future (S4), and identity that says what the system is and isn't allowed to become (S5) — checked by a function that never just takes the operators' word for it (S3*).

Why this matters specifically for an agent harness: the model is not a deterministic component. It changes across versions, has no memory of last quarter's incident, and treats a prompt as advice it can — and under pressure, will — ignore. A harness that regulates entirely through prompt text has exactly as much regulatory variety as the words in that prompt, which is provably less than the variety of a real codebase, a real filesystem, or real money moving. VSM doesn't remove the model's judgment; it gives that judgment a boundary it can't talk its way out of.

Six functions, one loop

Beer's Viable System Model, read as a harness architecture. Command flows down as attenuated instruction (grey); evidence flows back up as amplified fact (teal) — S3* audits S3 independently and verifies S1's units directly, never through what S1 reports about itself, and S4 scans the environment on its own channel, arguing with S3 about now vs. next on S5's terms.

Grey = attenuated instruction down the spine; teal = amplified evidence back up. S3* (alarm color) audits S3 independently and verifies each S1 unit's work directly — the dashed line bypasses S1's own report entirely. S4 scans the environment on its own channel, separate from the command spine.

Design goals and repository layout

Design goals

  • Keep the orchestrator small — the S3 loop of contract → dispatch → verify → route → close, generic over .
  • Declare the control plane rather than assemble it: , capability profiles, policy, and workload live in a versioned, checked definition.
  • Make S5 identity and policy durable and version-controlled, independent of any one context window.
  • Keep independent of S1 self-reporting.
  • Differentiate operations by , not roleplay persona.

Mechanism hierarchy

Prefer the mechanism that survives adversarial pressure

When adding a feature to the harness, regulator walks this ladder from the top down — reach for the highest level that can actually do the job, and only fall further down when it can't. If you can write the check, don't write the paragraph.

1
TypeScript invariant
Shape the data so the wrong value has nowhere to go — a fixed set of choices, not a free string anyone could mistype. The compiler refuses it before the code ever runs.
2
Deterministic runtime check
A rule enforced by code, every single time, whatever the prompt says — not a sentence someone has to remember to follow.
3
Structured tool / protocol
A fixed, validated shape for a request — no room to phrase around it, the way free text always leaves room.
4
Model judgment
Still a real decision point — the model is handed a specific question because nothing above can resolve it mechanically, like which category a merchant belongs to — and its answer still gets checked afterward, not simply trusted.
5
Prompt / context engineering
Not a decision point at all — ambient advice sitting in context that the model may or may not act on: house style, tone, a convention. Used only where being ignored costs little, since nothing here checks whether it was.
The orchestrator

A small loop, purpose-built for regulation

The orchestrator is nothing but the S3 loop — contract → dispatch → verify → route → close — generic over workloads, with leases, budgets and attempts as immutable records. It was built directly on bare Pi, one module per lesson: gates, effects, profiles, leases, contracts, budgets, recovery, audit and authority, with no workflow engine underneath it. The Pi-specific half lives in its own package, regulator-pi, behind a host seam: the control plane never imports a host, it resolves one by name. Workload-specific concerns stay out of the loop entirely, declared instead in a workload definition — which is what keeps the loop itself small enough to read in one sitting. How a unit runs through the loop is drawn out on its own page.

Status

Built end to end through lesson 15; the capstone is what's left

Four things are true today, each running end to end rather than sketched.

The loop runs. Contract, dispatch, verify, route, close — with , budgets, a versioned recovery policy, and a that trusts host-run evidence, never a unit's own claim about itself. An identity set is rendered from the files, write-protected, and checked at closeout against the branch.
The path is in. A unit can ask a person through one typed tool; only a nonblocking recap continues without an answer. An unanswered question pauses the unit by gate; what's owed to a person is delivered and reminded; who may answer is declared and checked.
The regulators owe evidence now. An eval harness runs the drift scenario under declared arms with outcome and trajectory graders. Four committed reports, one per scripted unit — the reference, the drifter, the sloppy one, and the self-certifier that deletes the tests it cannot pass — say where the gated arm loses. Every record carries an switch and a retirement condition, and every instance store reads as OpenTelemetry spans.
And it operates. The lab installs as a Pi package; regulator init installs it into an existing repository under a declared manifest; doctor checks the instance before the first unit and in CI; the base is re-verified after every merge and a failure holds the whole instance; refused words are linted out; the outbox is watched; an identity decision promotes back into the definition.

docs/DEBT.md tracks every gap the build has taken on deliberately, one row per item — forty-one rows so far, most already paid as later lessons closed them. What's still open, and worth knowing before you rely on this:

A live eval report is still owed. The four committed drift-scenario reports ran scripted units; the session's own gates — profile grants, the write gate, the bash watch, the budget guard — weren't exercised, so the numbers validate the graders, not yet a model against the harness.
The capstone rubric is specified, not calibrated. It hasn't yet been checked against a real learner submission.
Isolation is the container's job, not the harness's. bash sits outside the thrash detector, the effect journal, and the failure observer by design; real sandboxing is left to the operator, not built by the lab.
One machine at a time. Leases and the effect journal live on a single host; two harnesses on two machines can't yet see each other's intentions — that's deferred with full VSM recursion.
--by is asserted, not authenticated. Disposition authority checks whether the named person may decide, not that the caller is that person; authentication is the deployment's to add.

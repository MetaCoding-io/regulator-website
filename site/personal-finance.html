Worked example · a second workload, not software

"I want agents to manage my finances."

Follow the same six questions, in order, that turn that sentence into a declared workload: one mechanism per answer, then the files that declare it, then the commands that run it with the CLI. The point of doing this with money instead of code: none of the 's own logic had to change to support a household ledger — only new declaration files did. Everything here runs today, scripted, under the project's CI; the screenshots are the 's read-out of the result.

The goal

What these agents actually do, month to month

Strip away the control-system vocabulary for a moment. Once a month, this system is supposed to:

  1. Read the bank's statement — a CSV export the bank produces, dropped into a folder by hand.
  2. Sort every transaction into a category — groceries, rent, utilities — from a fixed list, not invented on the spot.
  3. Check the math — the categorized ledger has to add up to exactly what the bank statement says, row for row.
  4. Write a plain-English report — a short monthly summary a person can actually read.
  5. Draft a payment, then stop — e.g. "pay the landlord $1,800 on the 5th" — and wait for a person to say yes before anything is final. It never sends money on its own.

The rest of this page builds that system for real, in five steps: design it as a control system first, declare it as files, run it end to end, read the results back, and check it against what it honestly doesn't do yet.

Why this domain

A ledger is the mechanism hierarchy in miniature

The course builds regulator against a software repository because that is where agents are most common today. But the control plane is generic over workloads, and the fastest way to see which parts of the design are yours to make is to put a different domain under it.

A source of truth outside the harnessThe bank's statement. The harness reads it and must never write it. When the ledger and the statement disagree, the ledger is wrong.
Exactly one action that can hurtA payment. Consent has a concrete object, and "silence is not consent" has a concrete test.
Judgment on top of arithmeticWhich category a merchant gets is judgment. Whether the month balances is not — and can be checked without believing anyone.
The rule that makes it workNothing reads its own progress off the ledger. Whether August is closed is execution state; what the ledger contains is domain state; what was verified is regulatory state.
Step 1 of 5 · Design first

Six questions, and the level each answer sits at

For each function of the Viable System Model, ask the regulatory question it exists to answer, and answer it with a mechanism at the highest level of the hierarchy that fits — type → gate → typed tool → judgment → prompt — with a reason whenever it is not the top. "The agent will be careful" is not an answer.

Domain
What is the output, and where is the truth?Output: ledger/<period>.csv, reports/<period>.md, payments/pending/*.json. Truth: statements/, protected. The person's record: payments/executed/, protected. The domain's own checks: test/ledger.test.js — every category is in the taxonomy; every period balances to its statement row for row and in total; a report's totals are the ledger's; a pending payment is well formed.
What are the units of work, and what may each touch?Not "a finance agent". Six unit types — ingest, categorize, reconcile, report, prepare-payment, close — under two that are grants over declared tool effects. The bookkeeper writes under ledger/, reports/, payments/pending/ and gets no shell, so the grant is complete at the tool boundary. The auditor is read-only by declared effect. lib/ and test/ — the checks that will judge a unit — are under nobody's write grant.
What stops units tripping over each other?Unchanged from the lab: a lease per worktree, one period per unit, by the orchestrator, and the thrash detector — a category that flips between attempts is a coordination signal, not two edits.
What is a unit told; what is fixed, delegated, unresolved?A per unit. For categorize: fixed — the statement is not edited, the taxonomy is not extended; delegated — each row's category within the taxonomy, July as precedent, every new merchant reported; unresolved — UNKNOWN MERCHANT 8831, a 120.00 debit nobody can explain: defer. The unit does not guess; the close carries it as an open item. Budgets and routes per unit type in a policy file.
How do we know the close is right without believing the unit?The host runs the ledger's own suite against the committed revision and binds the result to unit, attempt, contract and revision; the report's claims satisfy nothing. identity-untouched diffs the protected prefixes against the base at closeout, so an edit committed around a gate is a failing check. glossary-lint reads the branch for the identity's refused words. inherited-tests runs the suite the unit inherited against the unit's tree, so a test cannot be deleted or weakened to make a close look right. After every merge the base is checked again, and a failure there holds the whole instance.
What in the environment matters?A statement arriving, a bill due, the tax calendar. Not automated here — the person drops the file in and dispatches the close. When it is, it is a research unit or the watcher raising an : intelligence starts a loop, it never is a decision.
What must the system never be able to do?Write the statement (outside the grant in the session; --protected statements/ at closeout). Write a payment file without a person's yes (ask_human with kind=consent opens a blocking obligation; the pause gate refuses every tool with an effect until it is answered; silence is never , by protocol constant). Write payments/executed/ (as the statement). In your own definition these are INV-005…007 in the identity, seeded into every instance and cited by contracts; the lab's identity is the software harness's, so the contracts here cite the person who fixed them, and the mechanisms are the same.
When must a person be interrupted?Once: before a payment file exists. The unknown merchant is not an interrupt — it is an open item, owed to a person as an obligation, delivered to the outbox, reminded, and it stops nothing. A question that waits and a question that does not are different kinds, and the kind is a typed field.

Step 2 of 5 · The declaration

A control plane is declared, not assembled

This is the whole implementation. Nothing in the orchestrator changed for it except one line: the CLI now loads the workload a contract names. Each file is in packages/regulator and checked by regulator check.

First, the domain — this already exists as a fixture, so there's nothing to invent: a taxonomy, a protected statement, a ledger, and the checks that will judge every unit's work, sitting outside every write grant.

household-ledger/                the domain: packages/regulator/fixture-finance
  categories.json               the taxonomy (the person's)
  statements/                   the bank's exports — protected
    2026-08-checking.csv/.json
  ledger/2026-07.csv            July, closed and categorized
  reports/2026-07.md            July's close
  payments/pending/             a file here is a commitment
  payments/executed/            what was paid — protected
  lib/ledger.js  test/          the ledger's own checks —
                                outside every write grant
  package.json                  scripts.test = node --test

Next, the capability profile — a grant over declared tool effects, not a persona. The bookkeeper gets no shell, so the grant is complete at the tool boundary; the advice is guidance for judgment calls, not a substitute for the two decisions above it.

profiles/bookkeeper.json
{
  "tools": ["read", "write", "edit", "grep", "find", "ls",
            "read_conventions", "run_tests", "run_checks",
            "remember", "ask_human"],        ← no bash
  "writablePaths": ["ledger/", "reports/", "payments/pending/"],
  "advice": [
    "…the statement is the bank's and is never edited…",
    "…a merchant you cannot explain stays in the holding
     category and is surfaced; do not guess.",
    "Writing under payments/pending/ is a commitment: ask_human
     with kind=consent … write nothing without a yes."
  ]
}

Then, the workload — six unit types, naming the profile each runs under and the checks the host will run at closeout. This is the one thing the orchestrator didn't already know how to do: load a workload other than the software one.

workload/personal-finance.json
{
  "name": "personal-finance", "version": 1,
  "unitTypes": [
    { "name": "ingest",     "profile": "bookkeeper",
      "checks": ["run_checks", "run_tests", "inherited-tests",
                 "identity-untouched", "glossary-lint"] },
    { "name": "categorize", "profile": "bookkeeper", "checks": [same] },
    { "name": "reconcile",  "profile": "auditor",
      "checks": ["run_tests", "inherited-tests", "identity-untouched"] },
    { "name": "report",     "profile": "bookkeeper", "checks": [same] },
    { "name": "prepare-payment", "profile": "bookkeeper", "checks": [same] },
    { "name": "close",      "profile": "auditor", "checks": [] }
  ]
}

Finally, a contract — one per unit; here's the one that touches money. The fixed decision below is the whole of INV-006 in miniature, cited to a person instead of an invariant file because this fixture has no identity fork of its own yet.

contracts/finance/f5-prepare-payment.json
{
  "unitType": "prepare-payment",
  "objective": "Prepare September's rent … after a person consents.",
  "fixed": [
    { "id": "f-consent",
      "decision": "No file is written under payments/pending/
        until a person answers yes to a consent question that
        names the payee, the amount and the due date.
        Silence is not consent.",
      "authorityRef": "human:alice" }      ← INV-006 in your fork
  ],
  "expectedEvidence": [
    { "class": "test",    "required": true,
      "description": "run_tests: the ledger's suite passes" },
    { "class": "command", "required": true,
      "description": "run_checks: protected prefixes untouched" }
  ]
}

Three more files exist in the real fixture, not shown above:

  • profiles/auditor.json — the read-only profile: read, grep, find, ls, read_conventions, run_checks. Nothing that writes.
  • policies/finance.json — budgets and model routes per unit type: the read-only unit types get one attempt each, and categorizing runs on the cheaper model.
  • contracts/finance/ — four more contracts, one per remaining unit type, in the same fixed / delegated / unresolved shape as the one above.
A shortcut this example takes This fixture borrows the software project's identity, so its fixed decisions cite a person (human:alice) instead of a written rule. If you built a standalone finance harness of your own, you'd instead write three permanent invariants into identity/INVARIANTS.md — INV-005 (the bank statement is never edited), INV-006 (nothing is committed to without consent), INV-007 (what was actually paid is the person's record, not a unit's) — and every contract would cite the invariant instead of naming Alice. The mechanism enforcing the rule is identical either way; only the paperwork changes.
Step 3 of 5 · Running it

Init, doctor, five units, one question

With the declaration from step 2 in place, this is every command from a bare fixture to a closed month — copy-paste order. Run it against the real fixture, or just read it: each line is annotated with what it does and why.

regulator fixture ~/ledger --finance
cd ~/ledger
regulator init --writable ledger/,reports/,payments/pending/ \
               --protected statements/,payments/executed/ --by alice
regulator doctor                                        # exit 1 on any problem

R=node_modules/@metacoding.io/regulator; L=$R/contracts/finance; P=$R/policies/finance.json   # the installed package's definition
regulator unit drive $L/f1-ingest.json --policy $P
regulator unit drive $L/f2-categorize.json --policy $P
regulator unit drive $L/f3-reconcile.json --policy $P
regulator unit drive $L/f4-report.json --policy $P
regulator unit drive $L/f5-prepare-payment.json --policy $P   # asks; nobody answers; pauses
regulator obligations                                   # consent: September rent — owed to a person, veto
regulator answer <obligation> --by alice --answer yes
regulator unit drive $L/f5-prepare-payment.json --policy $P   # the next attempt carries the answer
regulator-control-room --definition $R --instance ~/ledger   # @metacoding.io/regulator-control-room
  1. f1–f4The first four units succeed — but not on their own word. For each one, the host itself re-runs the ledger's real test suite — and the suite as it stood before the unit started, so a test the unit deleted or weakened counts against it — re-checks that no protected file (like the bank statement) changed, and scans for words the project has banned — all against the exact code the unit committed, not a summary of it. After each unit's work is merged in, the host runs the tests one more time on the combined result, just to catch anything the merge itself might have broken.
  2. Open itemOne transaction is left alone, on purpose. A $120 debit from a merchant nobody recognizes doesn't get a guessed category — the categorize unit marks it uncategorized and flags it in its report as unresolved. The ledger still balances to the bank statement byte for byte; that one row is just visibly unresolved instead of silently wrong.
  3. f5The fifth unit — the one that would pay rent — stops and asks first. Before it can write anything, it has to get a yes or no from a person ("pay the landlord $1,800 by the 5th?"). Nobody's answered yet, so it doesn't fail — it pauses, and the question sits in an outbox where a person will eventually see it. Nothing gets written until someone says yes. Once alice answers, re-running the same unit finishes the job and writes the payment file.
  4. CarelessNow try it with a version that cuts corners. This "careless" stand-in edits the bank statement directly and invents a category instead of using the real list. Its first attempt at every unit gets rejected — the tests fail, and a separate check independently notices the statement changed at all. The system automatically retries with a corrected attempt, which succeeds. The point: the bad edit never makes it into the real, merged result — it gets caught and discarded, not covered up.
  5. MemorySomething worth remembering gets remembered — narrowly. Along the way, the categorize unit learns "GREENGROCER 114 is the weekly grocery run" and saves it. But that fact is only ever shown back to the two unit types that need it (categorize and reconcile) — a unit doing something else, like preparing a payment, never sees it.
Checkpoint If you ran the commands above, you now have: a household ledger instance with five closed units and a sixth question answered; a merged ledger the bank's statement agrees with, byte for byte; one open item nobody guessed at; and a payments/pending/ file that only exists because a named person said yes. Nothing above required touching the orchestrator's code.

Step 5 of 5 · What it does not do

The honest limits of this example

Four ways this walkthrough is simpler than a real deployment would be — stated outright, not buried in a footnote.

It's a script pretending to be an assistant, not a live AIEvery unit above was completed by a small stand-in program — a "bookkeeper" and a "careless" one — not a real language model making judgment calls. That's on purpose: it means this exact scenario replays identically every time in the project's automated tests. The safety mechanisms that matter for a real AI session (limiting what it can touch, gating writes, pausing on a question) exist and are tested elsewhere; a live run with an actual model is the next drill, not this page.
Nothing automatically knows a payment is riskyThe system has no built-in sense that "write a payment file" is dangerous — the profile's written guidance just tells the assistant to treat it that way, and the assistant follows it. A stricter version would tag the "pay" action itself as irreversible, so a gate could enforce the pause automatically instead of relying on the assistant noticing. This example skips that on purpose: it has no tool that can actually move money, so there's nothing real at stake if it got this wrong.
The safety rules are tied to a person's name, not a permanent policyA standalone system would write its rules into a permanent policy file and have every rule cite that file. This example borrows the software project's setup instead, so its rules just say "because Alice said so." The mechanism enforcing the rule is identical either way — see the callout in step 2 — only the paperwork differs.
Nobody's watching for new statements, and open questions stay openA person still has to manually drop the bank statement in and kick off the process — nothing watches for a new file to arrive on its own. And that unrecognized $120 charge from step 3? It stays flagged forever in this example; nothing here ever resolves it. A fuller build could add a step that automatically asks a person to identify it.
Next · Your domain

The recipe

You've now followed a household ledger end to end — designed, declared, run, and read back. Here are the same eight moves, generalized, for whatever you're actually building.

  1. Name the domain output and the source of truth. Decide what is protected.
  2. List the unit types. For each: what it may write, which tools by effect, which host-run checks judge it. Put the domain's own checks outside every write grant; where a unit must be allowed to write tests, declare inherited-tests so the suite that judges it is the one it inherited.
  3. Write the checks. If the domain has no deterministic check of its own, you are about to build a system whose only verification is self-report. Stop and write one.
  4. Write the identity: the invariants, each with the mechanism that checks it, and the words the instance does not use.
  5. Write one contract per unit of the first piece of work: fixed, delegated, unresolved, expected evidence. Cite an invariant or a person for every fixed decision.
  6. Set budgets and routes per unit type. Decide who may answer what.
  7. regulator init with the declared prefixes; doctor; drive the first unit; read the evidence, not the summary.
  8. Script the close — a bookkeeper and a careless one — so it runs under CI, then run it live and compare. That is the eval harness pointed at your domain.

Nothing on this page was hypothetical, and neither is your domain's version of it. The fixture and every file in step 2 are real, checked-in code — start by reading them, not by starting from a blank file.
